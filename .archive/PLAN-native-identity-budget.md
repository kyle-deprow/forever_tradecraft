## Exact current call graph

For each update, `NativeCalibrationRunner.run` currently resolves identity in `calibration.py` before calling the provider (`identity_pre_provider`). `SessionDaemon._native_measurement_provider` then performs `_check_native_poll_identity`.

In the deferred construction path, `_check_native_poll_identity` first checks shutdown, construction context, reservation id/epoch and operation deadline. `_native_construction_validate_snapshot` then checks controller generation, Guardian generation, desktop lease, Guardian armed state, process owner/start, profile fingerprint, identity fingerprint, B0 and expiry, but also performs a full `driver.resolve_identity`; this was the uninstrumented 142.073 ms gap before the failed attempt's recorded `identity_poll` span.

The recorded `identity_poll` performs another full resolve and rechecks controller state/generation. `_capture_native_region_for_identity` admits current controller state/generation and the configured X11 backend. The driver backend performs fresh full resolves at `backend_pre` and `backend_post`, binds the exact rectangle and producer executable, proves the admitted owner process, and verifies output identity/digest. After acceptance, `capture_observation` performs independent `identity_post_capture`, then cells, runner decode, CRC/sequence/metrics and timing validation.

Thus an accepted deferred update currently has outer pre-provider, deferred owner-validation, provider poll, backend pre/post, and runner post-capture resolves. The first three are before the producer. Backend pre/post and runner post are the fresh pixel-bound proof sites. The update-1 pre-provider span occurred several seconds before accepted attempt 14 and must not be summed into it; update 2's outer span ended immediately before attempt 15.

## Candidate reduction and preserved proof

The first candidate is NATIVE-only and keeps the existing driver backend and runner post-capture fences unchanged. Eligibility is a closed daemon-owned predicate/token checked on every update: true only when the callable is the exact bound `_native_measurement_provider` installed by `SessionDaemon` at construction, the configured X11 telemetry-region backend is live, and the deferred context matches the current generation, run id, epoch, reservation id and original identity fingerprint. X11/configuration alone is insufficient. Custom or wrapped X11 providers and nondeferred contexts return false, preserving both outer/pre-provider and generic provider-poll resolves. Normal movement, legacy/fallback providers, and generic recovery revalidation retain their existing fresh checks.

1. Remove only the updates-loop full resolve immediately before the eligible configured deferred provider. Construct, held, resume, normal movement, fallback and arbitrary-callable paths are unchanged. The backend-pre resolve is fresher and rejects identity change before producer admission; backend-post and runner-post independently reject changes during/after capture.
2. In that eligible deferred provider path, and only for `stage == "updates"`, retain all cheap construction owner, controller, Guardian, lease, expiry, profile, B0, process-start and epoch checks, but return an immutable exact construction capability containing generation, run id, epoch, reservation id, Guardian generation, expected `ControllerState.NATIVE_CALIBRATION` and the original identity fingerprint. Compare the reservation fingerprint to the caller's originally verified fingerprint; this is not a vacuous self-comparison because backend-pre must then resolve the live client and compare its fresh fingerprint to that original before spawning the actual producer. The fast path is separate from generic recovery revalidation; existing `_native_construction_validate_snapshot` behavior remains intact elsewhere.
3. Remove the separate provider `identity_poll` full resolve only in that configured deferred path and only for `stage == "updates"`. Construct, held and resume keep their current poll resolve. Keep shutdown, context/epoch/reservation, controller state/generation and cheap owner checks. Backend-pre immediately follows and is the live identity/foreground/geometry admission fence for the exact producer.

No full identity result is cached across captures. The capability and expected NATIVE state/generation must thread from the eligible provider through `_capture_native_frame_with_capture` into `_capture_native_region_for_identity`; the current drop of those arguments is the defect to close. The capture path must recheck exact reservation/epoch/Guardian capability under its synchronized construction lock immediately before observer admission/Popen, so a revoke after cheap validation starts zero producer processes. Backend-pre still executes for every capture, backend-post proves the client did not change while the producer ran, and runner-post proves the retained PNG belongs to the same identity after decode. Owner process, executable digest, rectangle, lease, Guardian/generation, B0, source and cleanup checks remain at current boundaries. Identity changes before backend-pre, during capture, after backend-post, or during runner-post must still refuse.

The measured cross-shot arithmetic is `1384.571 ms`; it is a boundary model, not a universal guarantee. From accepted ordinal-1 capture start to failed ordinal-3 capture start, the exact nonoverlapping vector is: accepted producer 32.323 ms; backend-post 157.725; provider hash/decode 0.027/64.179; copy 0.437; runner hash 0.263; post-capture identity 224.612; cells 44.599; runner decode 54.788; validation/cleanup 0.229/0.173; accepted-path residual glue 0.847; next outer pre-provider 226.079; outer-gap glue 0.040; next deferred owner-validation 142.073; next provider poll 140.391; poll/backend-pre glue 0.167; backend-pre 178.006; backend-pre/request and request/lock glue 0.100; lock-to-shot setup 117.511. These values sum to the measured cross-shot boundary to rounding; nested backend barriers are not added to the enclosing capture span. The deterministic fixture must replay this named gen37 vector (trace digest `35c09833dda051ae0d6afd85d3190772c9d212c0ec7449148a399956c521ab60`) with an independent 1,000 ms publisher clock and real provider scheduling/ordinal logic. Report active critical work separately from deliberate publisher-alignment wait: active work must be <=900 ms for every modeled transition, while accepted capture spacing may be approximately 1,000 ms. The old graph must naturally miss at least one ordinal at the modeled boundary and report the actual pair; do not hardcode a 2->3 result whose exact publication instant is unknown. The live 100-update gate remains final; if modeled active work or live per-attempt timing fails, stop and propose a separately reviewed faster resolver. Do not alter cadence tolerance or remove another guard by inference.
