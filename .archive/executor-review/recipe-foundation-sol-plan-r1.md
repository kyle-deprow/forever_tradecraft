# Sol plan review: recipe foundation R1

The proposed three-file production fence is appropriately small for an offline foundation, and the plan correctly keeps catalog membership, client-data visibility, route quantities, server learnability, and launch market evidence separate. The implementation should remain limited to a strict loader/model, the two blocked current-build candidates, nine-row coverage, and deterministic refusal output. The following points must be closed before coding because they currently require the implementer to invent contract semantics.

## Must Fix

1. **Specify the exact JSON shapes and state invariants, including identity for unresolved records.** `PLAN-recipe-foundation.md:40-55` names `recipe_key`, `quantity_status`, per-threshold statuses, evidence status, cooldown variants, provenance claims, and unknown reasons without defining their JSON types, allowed enum values, null/omission rules, or cross-field invariants. In particular, an unresolved `recipe_key` is permitted for blocked records while names are forbidden as keys, so the two pilot candidates have no defined stable record identity. Add a compact canonical schema/example that defines every field and enum needed by the pilot. Use a stable internal `record_id` for review identity plus `recipe_id: positive integer | null`; define quantities as, for example, `quantity: positive integer | null` paired with `quantity_status: known | unknown`; and state exact rules for cooldown seconds/group, threshold values/statuses, acquisition evidence, vendor entries, tradeability, and `unknowns`. Define deterministic record, reagent, vendor-component, provenance-claim, and refusal-code ordering. This closes the strict-validation requirement without broadening the file fence.

2. **Freeze the evidence collection that the seed and validator are meant to verify.** Lines 52 and 58-66 require raw-content hashes, locators, build stamps, retrieval times, and field-level evidence, but the pilot at lines 76-85 identifies only live URLs and the plan does not name a snapshot/manifest path or digest. A `source_collection` object with one hash cannot be validated against several profession and item pages unless it identifies a concrete manifest. Before implementation, name one bounded snapshot manifest under the already allowed `.archive/executor-review/recipe-foundation-*` fence, list each retained page/snapshot ID, raw SHA-256, retrieval timestamp, claimed build, title, and permitted locators, and define how each normalized provenance claim references that manifest entry and its exact fields. `recipe_foundation.json` should bind the manifest's canonical digest. If the reviewed raw bytes are unavailable, keep the corresponding pilot facts blocked and do not label their quantities or thresholds as verified merely from remembered page content.

3. **Define or defer the market/recursive eligibility interface so this round remains implementable offline.** Lines 56 and 68-74 require compatible current quotes, recursive intermediate verification, vendor facts, and stable refusal codes, while acceptance test 7 requires stale-build/beta quote rejection. The plan does not define a quote/request type, freshness cutoff, output-item-to-recipe resolution, ambiguity/cycle behavior, optional-reagent treatment, or the refusal-code enum/order. The smallest valid choice is either: (a) keep this round recipe-only and return deterministic recipe-side blockers, explicitly deferring quote compatibility and recursive margin evaluation to the separately reviewed strategy slice; or (b) define a pure in-memory request contract containing the exact house, client version/build, interface or source revision, plan hash, observation time, explicit maximum age, and item-keyed quotes, plus fail-closed rules for missing/ambiguous producers and cycles. Do not let `recipes.py` import server storage or emit a numeric margin in this slice. Whichever choice is adopted, update tests 2, 4, and 7 to assert a named, ordered refusal-code set rather than leaving code names and precedence to the implementer.
