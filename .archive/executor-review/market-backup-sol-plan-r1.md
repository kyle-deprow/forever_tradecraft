# Sol plan review: market backup and restore R1

The dump-first/raw-second ordering is correct for the current ingest path: a format-2 archive is atomically renamed before its database reference can commit (`src/crowley/server/ingest.py:241-298`). A transactionally consistent `pg_dump` followed by a later read-only copy can therefore include extra immutable objects but must not miss any object referenced by the dump. The three-file fence is realistic, but the plan still leaves four safety-critical choices to the implementer.

## Must Fix

1. **Define dump-derived counts and the point at which a snapshot may be called complete.** `PLAN-market-backup-restore.md:20-23` requires schema/build/house/plan counts but does not say how they share the `pg_dump` snapshot, while `:35-39` and `:56-58` correctly prohibit checking references against the later live database. A query issued before or after `pg_dump` can observe a different ingestion commit. Require every expected table/regime/build/house/plan count used for acceptance to be queried from a disposable database restored from `database.dump`; never copy those values from the live source. Either have `snapshot` perform a minimal private restore before publishing its complete marker, or keep the snapshot manifest structural and put all dump-derived counts in a drill receipt bound to the snapshot digest. In the latter design, distinguish `complete backup bytes` from `restore-verified backup` explicitly. Do not publish live-query counts as expectations.

2. **Specify the Timescale-aware restore sequence.** “Compatible pinned Timescale/Postgres” at `:47-58` is insufficient for a full logical restore. The fresh target must create the database and TimescaleDB extension, run `timescaledb_pre_restore()`, execute a single-job custom-format `pg_restore` (no `-j`, with ownership handling fixed for the drill role), run `timescaledb_post_restore()`, and then `ANALYZE` before count/reference/API checks. Timescale's official logical-backup procedure requires the pre/post calls and explicitly warns against parallel `pg_restore`: [Timescale logical backup documentation](https://docs.timescale.com/self-hosted/latest/backup-and-restore/logical-backup/). Record PostgreSQL and Timescale extension versions from the restored database and compare them to the snapshot manifest. Start the server only after the base restore checks, using the recorded compatible server image/source and verifying that startup did not add an unreviewed migration before the authenticated read probe.

3. **Make isolation executable against the checked-in Compose file and use positive live-target refusal.** A new Compose project name alone is unsafe/infeasible because the base file publishes fixed host ports 5432 and 8080 (`deploy/docker-compose.yml:13-15,37-40`). Require an owner-only generated override that removes both published-port mappings, disables restart policies, uses project-scoped fresh volumes, and probes the API from the private drill network; no drill service may bind a host port. Generate the drill project name internally and refuse any pre-existing project. Before restore, inspect the current live Compose containers and mounts and record their exact container IDs, volume names/mountpoints, network IDs, and Compose labels. After creating the drill resources, require their project/service labels and mounts to match the generated drill identity and require all container, network, and volume identities to be disjoint from both current live identities and source identities recorded in the snapshot. Do not accept a destination container/volume name from the snapshot or operator. Recheck the same owned IDs immediately before cleanup so cleanup cannot broaden to a reused or unrelated resource.

4. **Define one backup layout and its raw-member/reference identity rules.** Lines 24-39 mention files, checksums, orphans, and durable publication, while `:54-55` assumes a tar-like extractor, but no canonical layout or trust boundary is defined. Specify an owner-only snapshot directory containing an initial `INCOMPLETE` marker, `database.dump`, one raw archive with only relative regular-file members, a canonical `manifest.json`, and a final `COMPLETE` marker that binds the manifest digest. The manifest must bind the byte size and SHA-256 of the dump and raw archive plus the exact raw member path/size/SHA-256 inventory; fsync files and directory before atomically publishing `COMPLETE`. Copy the live raw volume through a read-only mount, include only final files, and exclude dot-temporary ingest files.

   On restore, verify `COMPLETE` and every outer/member digest before creating targets; reject absolute paths, `..`, duplicates, links, devices, FIFOs, and unlisted or missing members. Convert database `raw_path` values only from the exact container `/data/` prefix to inventory-relative paths and reject every other path rather than opening it. From the restored dump, enumerate references from both `market_sweeps` and legacy `scans`. For format 2, require the referenced gzip to decode as the strict envelope, recompute the existing logical digest, and match database `content_digest`, content-addressed filename, sweep UID, house, plan hash, build/interface, and stored raw path. State the supported validation for any legacy row, or fail the snapshot/drill if a restored legacy reference exists until that format is defined. Classify unreferenced final objects as orphans, preserve and inventory them, and never let them satisfy a missing reference; referenced absence or identity mismatch fails. An invalid orphan may be retained as warned evidence, but it must not be reported as a validated market object.
