## Must-Fix

1. **The direct motion-key entrypoint is outside the stated capability gate and regression matrix.** `.archive/PLAN-native-motion-capabilities.md:117` enumerates camera calibration, camera dispatch, movement-basis calibration, and waypoint dispatch, while `.archive/PLAN-native-motion-capabilities.md:146` and `.archive/PLAN-native-motion-capabilities.md:184` likewise omit direct key dispatch. The omission is reachable: `src/crowley/session/cli.py:204` calls `SessionDaemon.execute_motion_key`, `src/crowley/session/daemon.py:2787` exposes it publicly, and `src/crowley/session/daemon.py:2908` performs its physical admission. An implementation conforming literally to the plan could therefore leave `motion_key` able to hold a movement key while CTM is enabled or native ground state is unknown/non-grounded. Add `execute_motion_key` and `_execute_motion_key_with_frame` to the daemon fence and required regressions. Require the same initial fresh gate, a newly observed successor recheck immediately before `run_motion_key_hold`, post-release state/binding validation, zero driver calls on refusal, and movement-basis invalidation on capability drift.

2. **The cited installed-client receipt does not contain the exact six predicate call signatures that the plan says it owns.** `.archive/PLAN-native-motion-capabilities.md:77` delegates the exact calls and signatures to the parent receipt, but `.archive/executor-review/native-api-parent-verification.json:15` contains only anonymous type/result arrays, and `.archive/executor-review/native-motion-api-provenance.md:8` lists function names without arguments or an ordered name-to-result mapping. This leaves the producer and harness free to agree on an unproved invocation, especially for any unit-taking predicate, while still passing all planned tests. Before implementation, pin the exact ordered expression and argument list for each of the six calls to the retained parent evidence, and make `tests/wow_harness.py` assert each function's arguments and one-call-per-publication behavior. Do not infer signatures from the model or from the harness itself.

3. **Capability drift invalidation is stated but not made exact or fully testable.** `.archive/PLAN-native-motion-capabilities.md:121` says drift invalidates the affected mapping or basis, while required regression 4 at `.archive/PLAN-native-motion-capabilities.md:187` only requires that camera drift leave no retained mapping admission and regression 5 at `.archive/PLAN-native-motion-capabilities.md:191` does not require clearing a retained movement basis. The current retained artifacts are independent long-lived fields at `src/crowley/session/daemon.py:310`; merely rejecting one call would allow an artifact established before the drift to be reused after capability state returns to allowed values. Define the invalidation matrix explicitly for initial-admission, immediate-precommit, and post-release drift, including which of `camera_mapping` and `movement_basis` is cleared for CTM and ground drift. Add assertions on the stored fields themselves after every drift branch, including failures raised while obtaining a successor frame.

## Should-Fix

1. **The speed tuple's numeric domain is internally inconsistent.** `.archive/PLAN-native-motion-capabilities.md:68` specifies only finite values, but `.archive/PLAN-native-motion-capabilities.md:181` requires negative values to be rejected and `.archive/PLAN-native-motion-capabilities.md:95` refers to an existing serialization bound without naming it for each tuple member. The current bound is `SPEED_LIMIT = 1000` in `addon/Crowley/Agent.lua:17` and `src/crowley/session/protocol.py:33`. State the exact nonnegative serialization range for all four tuple members and apply it identically in the producer and protocol validator; identify that range only as a wire-validation bound, never as a physical ceiling, unit conversion, or reason to treat the observed `run=7` as universal.

2. **The exclusive fence unnecessarily permits payload-boundary implementation changes.** `.archive/PLAN-native-motion-capabilities.md:138` allows changes to protocol payload-boundary handling even though `.archive/PLAN-native-motion-capabilities.md:35` requires CRS1, 2048-byte capacity, and the 2000-byte payload limit to remain unchanged. The boundary is already centralized by `MAX_PAYLOAD` and `CAPACITY` at `src/crowley/session/protocol.py:25` and enforced at `src/crowley/session/protocol.py:468` and `src/crowley/session/protocol.py:525`. Remove payload/framing handling from the mutable source fence and retain only boundary regressions proving exactly 2000 bytes is accepted and 2001 is rejected.

3. **The strict schema-3 cutover lacks an executable no-overlap sequence.** `.archive/PLAN-native-motion-capabilities.md:40` correctly forbids a dual decoder, but `.archive/PLAN-native-motion-capabilities.md:210` proceeds directly to addon deploy/reload without saying how the schema-2 producer and schema-3-only consumer are prevented from running against each other. Define a quiesced cutover: stop admission/consumption, place both reviewed producer and consumer code, reload the addon, require the first fresh identity-bound schema-3 frame, and only then resume the daemon entrypoints. This needs no compatibility fallback, deadline change, service redesign, or motion authority.
